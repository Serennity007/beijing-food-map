# render-check · 页面渲染证据

这些图是**内嵌 Chromium 实际渲染出来的**，用来回答"页面到底长什么样"，不替代 `docs/status.md` 的命令级 verified 账目。

拍摄环境（2026-09-24）：

- 视口 **530 × 567 CSS px**，DPR 1.5，Windows。命中仓库里 `max-width: 719px` 的窄屏断点。
- **不是真机**：360 / 390 / 430 这些手机宽度、软键盘顶起、触摸手势、安全区都还没验（见 blockers C10）。
- 数据通道：`1`–`3` 与 `5` 是静态模式（浏览器内引擎 + localStorage）；`4` 之后同一份产物被后端模式构建覆盖过，所以那几张不要拿来对比"模式差异"。

拍摄环境补充（2026-09-25，`8-` 这张）：内嵌 Chromium 的视口实测是 **531 × 568 CSS px**（`window.innerWidth`），也就是说它**命中 `max-width: 719px` 的窄屏断点，不是桌面宽度**。这纠正了 `docs/status.md` 与 `docs/handover.md` 之前把浏览器实测写成"桌面视口"的说法 —— 那几轮同样是在这个 530px 视口里做的，所以"窄屏断点下的后台面板"其实已经被走过一遍；仍然没验的是 360/390/430 这些真实手机宽度、软键盘顶起、触摸手势与安全区（blockers C10）。

**`-full` 后缀的是整页拼接图**：页面底部那条固定导航（`.tabbar`）会被重复画到拼接位置，看起来像压在正文上。
已用实测量坐标核对过：视口内导航占 508–567px，被"压"的那段文字在 214–262px，**没有遮挡，属截图伪影不是布局缺陷**。要看真实观感请用不带 `-full` 的视口图。

## 第一轮修改后的验证截图（2026-09-25，`9-`–`16-`）

拍摄环境（2026-09-25）：

- **真视口设置**：390×844 / 360×640 / 1440×900（`setViewportSize` 实设，不再是 530px 单一视口）。360/390 首次被真实验证（blockers C10 的手机宽度部分）。
- 数据通道：`9`–`13` 为后端模式（真实 HTTP + SQLite 独立库）；`14`–`16` 同一轮会话。
- **环境伪影，不要误报**：该内嵌浏览器在标签页被节流时，CSS transition 与地图相机动画会**冻结在中途**（实测抽屉高度停在 45dvh 起始值、相机停在中途坐标）。截图前注入了 `.drawer { transition: none }` 仅用于测量与截图；真实浏览器中这些动画 180–350ms 正常完成。布局数值均以动画结束后的稳态为准。
- 底图瓦片来自公共免费服务（OpenFreeMap / CARTO 兜底），本轮验证期间多次出现瓦片超时与 "API KEY REQUIRED" 水印，属**外部服务不稳定**，不是本仓库缺陷；`10` 一张恰好拍到 OpenFreeMap 正常渲染的稳态。
