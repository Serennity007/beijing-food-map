# 阻塞项与外部依赖

分三类：**要你提供/授权的（A）**、**上线前必须补的能力（B）**、**本轮刻意留下的缺口（C）**。
编号一旦发布就不再改动（其他文档按号引用），状态写在条目开头：`[已闭合]` 表示本机验过、`[未闭合]` 表示仍然挡着。
账目口径见 [status.md](./status.md)：`[未闭合]` 的每一项都是"未 verified"。

## A. 需要你提供凭据或授权（我无法自行完成）

1. **[未闭合] 高德 JS API 2.0 Key + 安全密钥**
   填 `VITE_AMAP_KEY` / `VITE_AMAP_SECURITY_CODE`（控制台里把 Key 限定到部署域名）。
   代码侧双适配器已实现并跑过纯函数单测，但**没有在真实地图上渲染过**。没有 Key 时走 MapLibre + 公共瓦片（OpenFreeMap / CARTO）兜底 —— 公共瓦片有配额与商用限制，只适合演示。

2. **[未闭合] 托管平台授权**
   `Dockerfile` 与 `render.yaml` 已写好但**未在任何账号上构建或导入**：这台机器没有 Docker，注册/创建服务/绑定域名都是操作你的账号。
   前端仓库的归属已确认：推到 `Serennity007/beijing-food-map`（public）。卡点是本机 `gh` 当前登录的不是该账号，而你要求"你先登录，我再推"。
   → 需要你在那台机器上执行 `gh auth login`（或 `git credential` 换成目标账号），之后我才能建仓、推 `main`、开 Pages。

3. **[未闭合] 真实门店与核验数据源**
   说明书的硬约束是不虚构门店、探店、票数。当前 24 家门店、71 条反馈、9 个账号全是合成种子，店名以「测试·」开头、`is_test_data` 恒为 true，production 配置下引擎直接拒绝装载。
   → 演示之外的一切都要先有经人工核验的门店库。这跟 C11 是同一件事的两面：既缺数据，也缺"把新门店走进核验流程"的功能。

4. **[未闭合] 短信服务凭据**
   `SMS_*` 变量是预留位。当前登录是内测账号 + 固定码 `888888`（只在非 production 生效）。

## B. 上线前必须补的能力（不补就不能算 production）

5. **[已闭合，附剩余尾巴] 会话签名**
   `apps/api/src/http/session.ts` 用 HMAC 签会话值，`SESSION_SECRET` 缺省时每次启动随机生成临时密钥（重启即要求所有人重新登录，这是默认的安全选择而不是漏洞）；`SESSION_TTL_SECONDS` 控制有效期（60—2592000），`COOKIE_SECURE` 已能从"只在 production"里独立出来按部署环境单独打开。签名/篡改拒绝/TTL 与 Cookie 属性由 `apps/api/test/session.test.ts` 覆盖。
   → 仍待做的：真实托管上要固定 `SESSION_SECRET` 并给出轮换流程（旧密钥保留一个验证窗口，避免轮换即踢掉全部在线用户），以及把密钥接进平台的 secret 管理。见 runbooks/deploy-api.md。

6. **[未闭合] 真实对象存储**
   图片是内联合成 data URI，`/media/:id` 做鉴权直出，`/uploads/test-photo` 只登记合成图。缺：真实上传的体积/类型校验、EXIF（含 GPS）剥离、缩略图、CDN、恶意内容处理。

7. **[未闭合] 持久化架构**
   `node:sqlite` 是单文件单进程：不能水平扩容；免费托管层的临时文件系统会在重新部署后清零（投稿与清单随之丢失）；登录限流是进程内滑动窗口，多实例等于限额乘以实例数。
   → 真实运营换 Postgres + 外部限流（`DATABASE_URL`、`SESSION_SECRET` 已在 `.env.example` 预留）。

8. **[已闭合，附剩余尾巴] 注销的清除任务**
   `deleteAccount()` 先做同步处置（撤销会话、撤销本人公开分享、隐藏 UGC、退出计票、写审计），`deleting` 账号行本身就是持久化任务；`Store.processDeletionJobs()` 幂等续跑，后端在启动时与每秒各排空一次，落库失败就回滚内存状态等下一轮；静态模式在 `StaticClient` 构造时排空、注销后 `setTimeout(0)` 再排一次。投稿/图片/清单/分享快照被真删，显示名与电话清空，只留去标识的用户行、举报状态与审计记录 —— 与隐私页与"我的"页现在的措辞一致。
   证据：`apps/api/test/handover.test.ts` 里"重启后继续完成注销"那条（第一次进程在清除前退出 → 库里停在 `deleting` → 第二个进程启动即续跑 → 本人旧分享 token 404、他人数据与种子分享链接仍在），加上 status.md 记录的浏览器实测（DELJOB0014 + 库内字段核对）。
   → 仍待做的：接真实对象存储后要补一条"删掉桶里字节"的任务步骤；审计记录的保留期到期后的匿名化脚本（现在按设计长期保留，用于复核）。

## C. 刻意留下的缺口（避免范围漂移）

9. **[已闭合只读部分] 审核侧举报队列**
   `Store.reportQueue(sessionId)` 用 `requireRole(['moderator','admin'])` 把关、最新在前、上限 200、条目带门店名；`GET /admin/reports` + OpenAPI 条目 + `Http`/`StaticClient` 两个实现 + `/admin` 的"举报复核"面板都在，卡片能一键跳到门店状态页预选该店。举报与状态的中文标签收进 `contracts/enums.ts`，"我的"页与后台读同一份。
   → 未闭合的是**处置闭环**：工单状态流转没有写接口（`REPORT_STATUSES` 已定义四种状态但只能由种子/门店状态操作间接改变）、举报不关联到具体反馈或媒体（现在只对门店）、没有重复举报的合并与限频、处理结果不会回写给举报人（"我的"页那条 `result_note` 是提交时给定的固定文案）。列为接手的第 2 优先级，见 handover §7。

10. **[未闭合] 真机与窄屏验证**
    桌面视口里的闭环（地图/投稿/清单/纠错/举报复核/注销）已在内嵌浏览器实测并通过，见 [status.md](./status.md) 的"浏览器实测看到的"。仍缺的是：窄屏断点下的布局、抽屉在手机上的遮挡与地图 inset、捏合与双指手势、读屏与键盘遍历 —— 内嵌浏览器只有一个固定桌面视口，这些没法在这儿采。
    → 需要你在手机/浏览器里打开一次（Pages 上线后就有地址），或者直接接受"桌面逻辑与界面已验、移动端未验"。

11. **[未闭合] 新门店没有提交核验入口**
    投稿只能在**已有门店**下产生反馈；第三方地点搜索回来的候选点不能建店，提交页对此写明了不提供入口。结果是新店只能靠 A3 的人工种子进库。
    → 这是阶段 1A 的范围，规则要在 `packages/contracts` 里加（候选 → `PENDING` 门店 → 三态核验 → 才进资格谓词），列接手的第 1 优先级，见 handover §7。
